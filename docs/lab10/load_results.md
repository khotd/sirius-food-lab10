## Как получены числа

Обычный сценарий: пауза 1–3 секунды. Стресс: пауза 0,01–0,05 секунды.
В обоих случаях веса запросов 7/2/1: список, карточка, создание заказа.
Spawn rate — 10 пользователей в секунду, разгон включён в длительность.
RPS и квантили взяты из *_stats.csv; это округлённые оценки Locust.
CSV пишется периодически и может немного отличаться от последней строки
итогового терминального отчёта. Сравниваются одинаковые поля сохранённых CSV.

API CPU включает родительский процесс и дочерние процессы Windows.
100% соответствует одному логическому ядру. У двух workers суммарное
значение закономерно может быть больше 100%.

## Найденное узкое место

При обычных пользовательских паузах 50–200 пользователей обслуживаются
без ошибок и без задержек p95 выше секунды. Поэтому порог насыщения
не следует выдавать за достигнутый в обычном сценарии.

При коротких паузах на одном worker самый медленный маршрут —
создание заказа: p95 1900 мс, тогда как у списка 710 мс.
Запись проходит аутентификацию, транзакцию БД и постановку уведомлений Celery.
Пиковая загрузка API — примерно 125% ядра, ожиданий блокировок PostgreSQL
в секундных выборках не обнаружено. Это указывает на ограничение обработки
в одном процессе API, а не на конфликт за баланс одного студента:
у виртуальных пользователей разные аккаунты.

Проверка гипотезы: тот же стресс-сценарий запущен на двух workers без
изменения бизнес-логики. Сравните строку двух workers с одним:
p95 создания снизился примерно до 500 мс, а пропускная способность выросла.
Это экспериментально подтверждает ограничение на стороне обработки API
на данном стенде. Оно не доказывает, что БД не станет следующим узким
местом при дальнейшем росте нагрузки. Отсутствие ожиданий блокировок
в секундной выборке также не исключает коротких ожиданий между выборками.

Первый практический шаг — несколько API workers с контролем ресурсов
и размера пула БД. Затем профилирование создания заказа и времени
синхронной отправки задач. Дополнительные workers нельзя бесконечно
добавлять без проверки нагрузки на PostgreSQL и Redis.

## Повторение

~~~powershell
$py = ".\.venv\Scripts\python.exe"
& $py -m scripts.run_lab10_load --seconds 50
& $py -m scripts.run_lab10_load --stress --users 200 --seconds 40 --output docs/lab10/load/stress
& $py -m scripts.run_lab10_load --stress --users 200 --seconds 40 --workers 2 --output docs/lab10/load/two_workers
~~~

Каждая команда создаёт собственную временную среду. Выполняйте их по
очереди, без других нагрузочных прогонов. HTML-отчёты создаются рядом с CSV
и остаются локальными. Сырые выборки CPU/БД — в *_resources.json.
