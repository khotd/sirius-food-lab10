# Защита практической работы № 9 — наблюдаемость

Уровень: **8 баллов**. Запустите ЛР № 7 и сервисы мониторинга по [инструкции](start_labs_6-9.md#5-лр--9-prometheus-grafana-и-логи). API и кухня должны писать stdout в отдельные файлы `api.log` и `kitchen.log`. Держите демо-курьера свободным для успешного сценария.

## 1. Запрос и прохождение события

```text
python -m scripts.demo_orders --correlation-id demo-42
```

Скрипт отправляет **два HTTP-запроса** с одним заголовком: создание и оплату. Именно оплата запускает событие доставки и кухни из ЛР № 7. Скрипт проверяет, что ответ каждого запроса вернул `X-Correlation-ID: demo-42`. Запишите ID заказа. Если хотите показать сами заголовки в Network или curl, выполните эти же операции через Swagger и curl; `curl.exe -i -H "X-Correlation-ID: demo-42" http://127.0.0.1:8000/menu/items` также наглядно показывает эхо заголовка.

В PowerShell найдите записи с точным значением (из корня проекта):

```powershell
Get-Content api.log, kitchen.log |
  ForEach-Object { $_ | ConvertFrom-Json } |
  Where-Object { $_.correlation_id -eq "demo-42" } |
  Format-Table timestamp, service, event, order_id, event_id
```

В bash: `grep -F '"correlation_id": "demo-42"' api.log kitchen.log`.

Покажите `order_created` и `order_paid` в монолите, `order_received` у кухни, один и тот же `order_id` и ID корреляции. Если нужны детали пути, найдите этот же ID в stdout outbox и доставки. Объясните: middleware валидирует заголовок или создаёт UUID; outbox хранит его до отправки; publisher кладёт ID в AMQP headers; consumer извлекает его и пишет в JSON.

## 2. Проверка панели и расследование

1. Откройте [Prometheus Targets](http://127.0.0.1:9090/targets): `sirius_app` и `rabbitmq` — **UP**. Откройте [дашборд](http://localhost:3001/d/sirius-lab9). Покажите RPS создания и оплаты, p95 меню, частоту 5xx, глубину очереди кухни и долю попаданий Redis. Ноль у 5xx — штатный результат без ошибок.
2. Откройте меню и дайте Prometheus собрать не менее двух точек. Для всплеска RPS после первого сбора повторите оформление с другим ID, например `demo-43`. Для изменения p95 и hit rate в PowerShell выполните `1..30 | ForEach-Object { Invoke-RestMethod http://127.0.0.1:8000/menu/items | Out-Null; Start-Sleep -Milliseconds 300 }`. Чтобы показать ненулевую глубину очереди, ненадолго остановите только кухню, оформите заказ, дождитесь следующего сбора метрик и запустите кухню обратно.
3. Возьмите UTC-время `order_paid` из JSON и покажите этот интервал в Grafana (например, Last 5 minutes). Логи показывают **конкретный заказ**, панели показывают **всю нагрузку за интервал**. Длительность отдельного запроса возьмите из `duration_ms` соседней записи `http_request`; p95 не является длительностью этого заказа.

**Вопросы.** Мониторинг отвечает на заранее заданные вопросы, наблюдаемость помогает объяснить неизвестный заранее сбой. Correlation ID передаётся с бизнес-операцией между процессами, trace ID связывает технические интервалы трассы; span — один интервал, trace — их дерево. Context propagation — передача контекста через транспорт. JSON в stdout можно собирать и фильтровать по полям. RED — Rate, Errors, Duration. В метках используются шаблоны маршрутов и статусы: ID заказа и корреляции создали бы отдельный временной ряд для каждого запроса. `scope["state"]` (доступен как `request.state`) переносит ID в обработчик, а вызов ASGI-приложения передаёт запрос дальше. Sentry группирует исключения и прикладывает контекст; для этой работы он не требуется.
