# Учебная практика Сириус Еда

Реализованы трек A «Промокоды и лояльность» и трек D «Платёжная интеграция»
в объёме требований на 8 баллов. Результат — REST API с JWT и RBAC,
миграция PostgreSQL, обработчики RabbitMQ, автоматические тесты и стенд Docker Compose.
Защита проводится через Swagger и просмотр состояния БД.

## Соответствие заданию

| Трек | Требование | Реализация |
|---|---|---|
| A | Модель промокода | `PromoCode`, уникальный код, тип скидки, сроки, лимиты, минимальная сумма, активность |
| A | Атомарное применение | Создание заказа, резерв денег, списание баллов и `PromoCodeUsage` в одной транзакции |
| A | Защита от гонки | `SELECT FOR UPDATE` пользователя, промокода и счёта; лимит проверяется под блокировкой |
| A | Начисления и уровни | Consumer `loyalty`, Bronze 3%, Silver 5%, Gold 7%; уникальный `earn_order_*` |
| A | Частичная оплата баллами | `loyalty_points`, не более 50% суммы после скидки, уникальный `spend_order_*` |
| A | Saga отмены | Outbox `order.cancelled`, отдельные consumers `loyalty` и `promo`, компенсационные ключи |
| A | Истечение срока | Ленивая проверка: `valid_from <= now < valid_until`; отдельный Beat не требуется |
| D | Внешний шлюз | Реальный адаптер Stripe PaymentIntents API, только ключи `sk_test_*` |
| D | Инициирование | `POST /payments`, сумма сверяется с заказом, уникальные ключ и `order_id` |
| D | Вебхуки | Подпись HMAC-SHA256 по исходному телу, окно 300 секунд, только тестовые события |
| D | События | `payment_intent.succeeded`, `payment_intent.payment_failed`, `refund.created/updated` со статусом `succeeded` |
| D | Retry | Пять попыток; 1, 2, 4, 8 секунд + jitter; неизменный Idempotency-Key; 5xx, 429, transport error, timeout |
| D | Исчерпание retry | Запись `failed` с безопасным `error_code`, без повторного создания PaymentIntent |
| A и D | Уровень 8 | Тесты правил, HTTP, повторов, ошибок шлюза, подписей; проверки конкуренции на PostgreSQL |

Автоматический вызов refund при отмене внешнего платежа, нагрузочные тесты
и ADR относятся к расширению D на 10 баллов и не входят в этот объём.
Полный возврат можно выполнить в тестовом Stripe Dashboard: подписанный вебхук
отменит заказ и запустит компенсации A. Частичные возвраты в этом MVP не поддерживаются.

## Запуск

Нужны Docker Desktop и файл `.env`. Для нового клона:

```powershell
Copy-Item .env.example .env
# Установите свой SECRET_KEY, DEBUG=True и PRACTICE_DEMO_PASSWORD в .env.
docker compose up --build -d
docker compose exec api python -m scripts.seed_practice
```

Swagger: <http://localhost:8000/docs>. Compose запускает миграцию до API,
PostgreSQL, Redis, RabbitMQ, delivery, outbox, kitchen, delivery-consumer,
payment-consumer, loyalty, promo и Celery. Существующий `.env` не заменяйте:
добавьте в него новые параметры из `.env.example`.

Для существующей БД с учтёнными миграциями выполняется `alembic upgrade head`.
Если старая база была создана только через `create_all`, сначала установите
фактическую ревизию её схемы; не используйте `stamp head` без сверки.
Тестовые стенды создавайте отдельно от рабочей БД.

В seed создаются пользователи `practice-student@sirius.ru`,
`practice-admin@sirius.ru`, `practice-cook@sirius.ru`, `practice-courier@sirius.ru`.
Пароль берётся из `PRACTICE_DEMO_PASSWORD`; студент получает 5000 на внутренний
баланс и 100 учебных баллов только при первом создании. Добавляются блюдо за 200,
промокоды `PRACTICE10` (10%) и `PRACTICE50` (50 денежных единиц).

## Архитектура

```text
HTTP → router → service → repository → PostgreSQL
                   ↓
              gateway adapter → Stripe test API

Оплата → [order.paid + outbox] → RabbitMQ → loyalty → earn
Отмена → [order.cancelled + outbox] → RabbitMQ
                                      ├─ loyalty → refund + revoke
                                      └─ promo → restore usage
```

Сервисы не импортируют FastAPI, SQLAlchemy или конкретные репозитории.
Роутеры валидируют транспорт, проверяют роли и переводят ошибки в HTTP.
Репозитории выполняют SQL; gateway изолирует HTTP к Stripe. Публикация outbox
и результат обработки consumer фиксируются вместе с бизнес-изменениями.
ACK выполняется после commit; некорректные события уходят в существующую DLQ.

Сумма заказа `charged_amount`, снимок исходной цены, скидка, баллы и платежи
хранятся как `Numeric(12,2)`. Расчёты выполняются через `Decimal`, округление —
до сотых, `ROUND_HALF_UP`. Исторические поля внутреннего денежного баланса
и каталожной цены сохранены как Float ради совместимости лабораторных;
при оформлении они переводятся в Decimal до расчёта.

Принятые правила: Silver начинается с 1000 начисленных баллов, Gold — с 3000;
ставка берётся по уровню до начисления. Баллы начисляются на денежную часть
после скидки и списания баллов. При отмене накопленные начисления уменьшаются,
уровень пересчитывается. Если заработанные баллы уже потрачены в другом заказе,
отзыв может сделать баланс отрицательным: это долг, который погашают следующие
начисления; списывать дополнительные баллы при долге нельзя.

## Защита трека A

1. В `POST /auth/login` войдите как студент; access token вставьте в Authorize.
2. В `GET /menu/items` найдите ID учебного блюда. `GET /loyalty/me` покажет счёт.
3. Создайте заказ:

```json
{"item_id": 1, "quantity": 1, "promo_code": "PRACTICE10", "loyalty_points": "50.00", "payment_method": "balance"}
```

Подставьте фактический ID блюда. Для цены 200 получится скидка 20,
списание 50 баллов и денежная часть 130. На счёте останется 50 баллов.
`charged_amount` фиксируется и не меняется при последующем редактировании меню.

4. `POST /orders/{id}/pay` подтверждает резерв. Consumer начислит 3.90 балла Bronze.
   Повтор `/pay` не создаёт новое событие и не списывает деньги.
5. Для демонстрации ручной отмены используйте ещё не переданный курьеру заказ:
   `POST /orders/{id}/cancel`. Он возвращает денежный резерв и записывает outbox.
   Уже доставленный или переданный курьеру заказ отменить нельзя.
   Если свободного курьера нет, прежняя Saga доставки автоматически отменяет
   внутреннюю оплату и запускает те же компенсации.
6. После consumers `GET /loyalty/me/transactions` показывает `spend`, `earn`,
   `refund`, `revoke`; счёт возвращается к исходным 100, использование промокода снято.
   Для отмены до оплаты будут только `spend` и `refund`.
7. Повторное применение использованного одноразового промокода, истёкший срок,
   недостаток баллов и попытка оплатить более 50% возвращают 400 без частичного списания.
8. Создание промокодов: `POST /loyalty/promos`, только роль admin. Сроки задаются
   с часовым поясом, например `2026-11-23T00:00:00+03:00`.

Компенсации асинхронны: дождитесь consumers перед повторным использованием
промокода. Ключи компенсаций уникальны по заказу, поэтому защита работает и
при двух событиях отмены с разными `event_id`.

## Подключение Stripe в тестовом режиме

Нужен собственный Stripe test account. Секреты добавьте в `.env`:

```dotenv
STRIPE_SECRET_KEY=sk_test_ваш_ключ
STRIPE_WEBHOOK_SECRET=whsec_из_stripe_listen
PAYMENT_CURRENCY=rub
```

Суммы учебного каталога трактуются в указанной валюте. Поддержка валюты зависит
от тестового аккаунта; при необходимости используйте `usd` и соответствующие цены.
Перезапустите API после изменения переменных:

```powershell
docker compose up -d --force-recreate api
stripe listen --events payment_intent.succeeded,payment_intent.payment_failed,refund.created,refund.updated --forward-to localhost:8000/payments/webhook
```

Возьмите `whsec_...` из вывода Stripe CLI, внесите в `.env` и ещё раз пересоздайте API.
CLI должен работать в тестовом режиме того же аккаунта, что и `sk_test_*`.

## Защита трека D

1. Создайте заказ с `payment_method: "external"`. Внутренний денежный баланс
   не списывается; промокод и баллы резервируются так же, как в A.
2. `POST /payments`: тело `{"order_id": 1, "amount": "200.00"}`,
   заголовок `Idempotency-Key: practice-payment-1`. Подставьте реальный ID и
   окончательную сумму после скидки и баллов. Получите `gateway_payment_id`
   и `client_secret`; статус остаётся pending до вебхука.
3. Повторите запрос с тем же телом и ключом: ID платежа тот же. Другая сумма
   или другой заказ с уже занятым ключом дают 409. Чужой заказ даёт 403.
4. Подтвердите созданный PaymentIntent в тестовом режиме через Stripe CLI:

```powershell
stripe payment_intents confirm pi_ПОДСТАВЬТЕ_ID --payment-method pm_card_visa
```

5. Подписанный `payment_intent.succeeded` переведёт заказ в paid, запишет
   ровно один `order.paid`, затем consumer A начислит баллы.
   Результат смотрите в `GET /payments/{id}` и `GET /loyalty/me`.
6. Для отказа используйте новый заказ и тестовый payment method
   `pm_card_chargeDeclinedInsufficientFunds`; ожидается `failed/insufficient_funds`.
   Повторное подтверждение того же PaymentIntent с успешным методом может
   завершиться успехом; старый failed-вебхук не откатывает succeeded.
7. Отправьте поддельный `Stripe-Signature`: 400. Повторите настоящий вебхук
   через Stripe Dashboard: повторный `event_id` игнорируется. Даже отдельное
   событие успеха для того же PaymentIntent не создаёт вторую оплату/outbox.
8. Сделайте полный refund в тестовом Stripe Dashboard: refund-событие со
   статусом succeeded отменит заказ и запустит возврат баллов/промокода.
   Позднее событие успешной оплаты не воскресит отменённый заказ.

После начала внешнего платежа обычная отмена блокируется: PaymentIntent может
ещё завершиться у шлюза. Для возврата используйте тестовый Dashboard.
При неопределённом исходе timeout новая попытка с другим ключом блокируется;
повтор POST возвращает сохранённую ошибку. Поздний подписанный вебхук может
восстановить платёж по ключу из metadata. Если процесс упал до commit ответа
Stripe, повторите исходный POST с исходным ключом: Stripe вернёт тот же объект.
Если доставка внешне оплаченного заказа не назначена, consumer пишет
`external_refund_required`; оператор выполняет полный refund в Dashboard.

## Тестирование

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest tests/practice tests/test_architecture.py -q
```

Без внешних служб используются SQLite и `httpx.MockTransport`: проверяются
реальные сервисы, SQLAlchemy-репозитории и HTTP-роутеры. Три теста блокировок
и consumer-handler требуют PostgreSQL и пропускаются на SQLite.

Для проверки PostgreSQL создайте **отдельную временную БД**; фикстуры удаляют
и создают таблицы. Имя обязательно начинается с `practice_test_`:

```powershell
docker run -d --name sirius-practice-test-db -e POSTGRES_USER=practice -e POSTGRES_PASSWORD=practice -e POSTGRES_DB=practice_test_ad -p 127.0.0.1:55439:5432 postgres:15-alpine
$env:PRACTICE_TEST_DATABASE_URL="postgresql://practice:practice@127.0.0.1:55439/practice_test_ad"
python -m pytest tests/practice tests/test_architecture.py -q
Remove-Item Env:PRACTICE_TEST_DATABASE_URL
docker rm -f sirius-practice-test-db
```

Ключевые проверки: два покупателя конкурируют за последнее применение,
параллельные одинаковые платежи вызывают шлюз один раз, consumers возвращают
баллы и промокод один раз. Отказы сети и задержки проверяются управляемыми
ответами транспорта без ожидания реальных таймаутов.

Реальный вызов Stripe требует пользовательских тестовых ключей; автоматические
тесты не обращаются к аккаунту и не выполняют реальные списания.

Проверка реализации 23 ноября 2026 года: 111 тестов прошли, включая 50 проверок
практики и архитектуры на PostgreSQL и регрессию прежних сервисов.
Миграция проверена вперёд и назад; `alembic check` не обнаружил расхождений
с ORM. Конфигурация `docker compose config --quiet` валидна.
Docker-образ собран; на временном стенде с PostgreSQL, Redis и RabbitMQ
проверен HTTP-сценарий: вход → заказ со скидкой и баллами → оплата →
начисление consumer → отмена → refund/revoke → повторное использование промокода.

## Вопросы для устной защиты

- Почему Decimal? Десятичное округление должно совпадать с денежной суммой до копейки.
- Зачем блокировать промокод? Уникальный код не защищает остаток лимита от двух конкурентных проверок.
- Чем Saga отличается от SQL-транзакции? Между обработчиками нет общей транзакции;
  отмена публикует событие, каждый участник выполняет свою компенсацию.
- Почему недостаточно event_id? Два разных события могут описывать одну отмену;
  уникальные ключи `refund_order_*`, `revoke_earn_order_*`, `restore_promo_order_*`
  защищают бизнес-результат.
- Почему сумма берётся из заказа? Клиент не должен уменьшить сумму перед вызовом шлюза.
- Почему POST не помечает заказ paid? Создание PaymentIntent ещё не означает успешную оплату;
  источником подтверждения служит подписанный вебхук.
- Зачем одинаковый ключ на retry? Ответ мог потеряться после выполнения запроса;
  новый ключ мог бы создать второй платёж.
- Что делать с failed после timeout? Это неопределённый результат; ждать вебхука или
  сверять тот же PaymentIntent, а не создавать новое списание.
